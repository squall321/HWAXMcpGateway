# search_tools 의미 순위 — 평가셋과 견주기

게이트웨이 `search_tools` 의 지금 순위(부분문자열 점수 + 손으로 늘리는 동의어 `_SYN`)와, 거기에 AIDataHub 임베딩 순위를 RRF 로 더한 순위를 **같은 평가셋**으로 견준 기록이다. 옵션은 기본 꺼짐이고 켤지는 이 숫자를 보고 사람이 정한다(HWAXPortal `docs/improvement-1015` §2 4).

## 결과 — 2026-10-16, dev

- 카탈로그 — dev 게이트웨이 스냅샷(백엔드 도구 430개 + 로컬 10개). DynaForge(`heax-kooremapper_mcp`) · ReportArchive · `smart-twin-cluster` 가 닿지 않던 때라 그 도구가 정답인 doc 8쌍은 빠졌다(150쌍 중 142쌍).
- 임베더 — dev AIDataHub `/api/embed`(multilingual e5-base, 768차원, CPU 로 돈다). 도구 글은 '앱 라벨 · 이름: 설명' 전문이고 RRF 상수는 60 이다(코드 그대로).

| 방법 | 출처 | n | hit@1 | hit@5 | MRR@20 |
|---|---|---|---|---|---|
| 부분문자열(지금) | doc | 34 | 0.471 | **0.882** | **0.651** |
| RRF(옵션) | doc | 34 | 0.382 | 0.706 | 0.539 |
| 임베딩만(진단) | doc | 34 | 0.147 | 0.412 | 0.255 |
| 부분문자열(지금) | auto | 108 | 0.194 | 0.389 | 0.298 |
| RRF(옵션) | auto | 108 | 0.296 | **0.713** | 0.466 |
| 임베딩만(진단) | auto | 108 | 0.380 | 0.667 | 0.495 |

쌍마다 견주면(RRF 대 부분문자열, 정답 순위) doc 은 나아짐 4 · 나빠짐 13 · 같음 17, auto 는 나아짐 69 · 나빠짐 10 · 같음 29 다. 두 출처를 합친 수(142쌍)는 auto 108쌍 쪽으로 기울어 싣지 않는다 — 출처별로 읽는다.

doc 을 둘로 나누면 무엇이 지는지 보인다.

| doc 묶음 | n | 부분문자열 hit@5 | RRF hit@5 | 쌍마다 |
|---|---|---|---|---|
| 심의 업무 낱말(doc-01~14 — 이미 `_SYN`·APP_META 로 고친 낱말) | 14 | 1.000 | 0.571 | 나아짐 1 · 나빠짐 8 · 같음 5 |
| 그 밖(오배정 실사고 · 어휘 0건 질의 · 문서가 적은 짝) | 20 | 0.800 | 0.800 | 나아짐 3 · 나빠짐 5 · 같음 12 |

지는 꼴은 하나다 — 짧은 한국어 업무 낱말('안 선택' · '신뢰 판정' · '해석 설계')은 임베딩이 엉뚱한 도구를 위로 올리고(정답이 20위 밖), RRF 는 두 순위에 함께 든 도구를 한쪽 순위에만 든 도구보다 앞세우므로 부분문자열이 2위로 잡은 정답이 그 잡음에 밀린다. auto 에서 진 10쌍도 대개 같은 꼴이다(7쌍은 정답이 임베딩 20위 밖이었다). 거꾸로 이기는 곳은 설명을 바꿔 말한 문장('PCB 휨 불량' 9위 → 1위 · '굽힘반경을 지정해 층별 응력' 6위 → 2위)이다.

시간 — `search_tools` 한 번이 부분문자열은 중앙 8~10ms(p95 12~16ms), RRF 는 중앙 387~406ms(p95 615~828ms · 최대 1,038~1,089ms)다(142쌍을 두 번 잰 범위). 늘어난 것은 거의 전부 임베더 왕복이고(게이트웨이 안의 계산 — 해시와 내적 440개 — 은 중앙 21ms) 박스 부하를 탄다 — 같은 날 doc 34쌍만 잰 앞선 실행은 p95 2,729ms · 최대 5,195ms 였다. 세 번 모두 같은 AIDataHub 를 부르는 다른 평가(한국어 검색 기준선)가 돌던 때라 한가할 때의 값이 아니다 — 적중 수는 잴 때의 한도가 30초라 영향이 없다(강등 0). 그런 때는 질의 한도 기본 2초를 넘는 호출이 생기고, 넘은 호출은 부분문자열 순위로 답한다(결과의 `mode_reason` 이 말한다). 색인은 도구 440개에 100~172초다(dev CPU — 재집계 뒤 뒤에서 돌고, 그동안 검색은 부분문자열로 답한다).

## 읽는 법 — 순환성과 한계

1. **auto 쌍은 도구 설명에서 썼다 — 임베딩에 유리하다.** 설명의 뜻을 옮긴 문장이라 설명 전체를 임베딩한 벡터와 가깝게 놓인다. 순위 방법을 모르는 별도 에이전트가 쓰고 세 어절 이상 옮기지 못하게 했지만 순환은 남는다. 실사용 질의는 더 짧고 업무 낱말이 많아 doc 쌍에 가깝다. auto 의 큰 개선(hit@5 0.389 → 0.713)을 실사용의 개선으로 읽지 않는다.
2. **doc 34쌍 가운데 14쌍은 이미 손으로 고친 심의 낱말이다 — 지금 방식에 유리하다.** 그래서 위 표에서 따로 나눴다. 그 묶음을 빼도 RRF 는 doc 에서 이기지 못했다(hit@5 같음, MRR 0.591 → 0.627 로 조금 나음).
3. **정답이 좁다.** doc 정답은 그 문서가 쓰일 때의 카탈로그 기준이라 지금 440개 가운데 다른 맞는 도구를 놓침으로 센다(예 '판재가 휘는 문제' → `slenderness_check` 도 맞는 답이다). 임베딩이 그런 다른 답을 더 자주 낸다 — 사람이 정답을 넓히면 RRF 쪽 수가 오를 수 있다.
4. **n 이 작다** — doc 한 쌍이 약 3%p, auto 한 쌍이 약 1%p 다. 모든 쌍이 `reviewed: false` 다.
5. **호출 수 가중은 넣지 않았다** — 게이트웨이는 도구별 호출 수를 세어 두지 않는다(감사 원장에 줄로만 있고 `search_tools` 자체는 감사 밖이다).

## 진단 — 바꿔 본 것(코드는 고르지 않았다)

같은 평가셋으로 손잡이를 고르면 그 평가셋에 맞춘 값이 된다. 코드는 관례값(RRF k=60 — 에이전트 서버 `_rrf` 와 같다 · 도구 글 전문)을 두고, 바꿨을 때의 수만 적는다(캐시한 벡터로 같은 쌍을 다시 쟀다).

| RRF 를 바꾸면 | 심의 낱말 hit@5 | doc 그 밖 hit@5 | auto hit@5 |
|---|---|---|---|
| k=60(지금) | 0.571 | 0.800 | 0.713 |
| k=30 | 0.714 | 0.850 | 0.713 |
| k=10 | **1.000** | 0.800 | **0.722** |
| k=60 · 부분문자열 순위 가중 2 | 0.929 | 0.850 | 0.593 |

| 도구 글을 바꾸면(k=60) | doc hit@5 | auto hit@5 |
|---|---|---|
| '앱 라벨 · 이름: 설명' 전문(지금) | 0.706 | 0.713 |
| 같은 꼴, 설명 앞 400자 | 0.706 | 0.731 |
| '이름: 설명 앞 400자'(에이전트 서버의 도구 임베딩과 같은 꼴) | 0.765 | 0.639 |

k 가 작으면 각 순위의 1·2위가 무거워져 부분문자열이 잡은 정답이 잡음에 덜 밀린다. 도구 글의 꼴은 두 출처에서 엇갈려 고를 근거가 없다.

## 판단에 쓸 것

- **지금 꼴(k=60) 그대로는 켜지 않기를 권한다.** 문서에 남은 심의 업무 낱말이 14쌍 중 8쌍 밀린다(hit@5 1.000 → 0.571).
- k=10 이면 이 평가셋에서 그 회귀가 사라지고 auto 의 개선은 남았다. 다만 같은 쌍으로 본 값이다 — 사람이 쌍을 검토하고(`reviewed: true`, 정답 넓히기) 실사용 질의를 모아 다시 잰 뒤에 정한다. 바꾸는 자리는 `gateway.py` 의 `_TOOL_RRF_K` 한 줄이다.
- 임베딩만으로는 doc 에서 크게 진다(hit@5 0.412) — 갈아 끼우는 것은 답이 아니다(제안 문서의 경고와 같다).

## 평가셋 — `pairs.jsonl`

한 줄에 한 쌍이다 — `{id, query, gold, source, reviewed, ref, note?}`.

- `gold` 는 정답 도구 목록이고 하나라도 순위에 들면 맞힌 것이다. 이름은 `앱키:원래 도구 이름` 이다 — 노출 이름은 같은 이름의 다른 앱이 떠 있느냐에 따라 접두(`ste_`·`heaxstep_forge_`)가 붙었다 떨어졌다 해서 그대로 쓰면 평가셋이 카탈로그 상태를 탄다.
- `source: doc` — 문서와 커밋에 남은 사례에서 옮겼다(`ref` 가 출처, `note` 가 그때 일). 오배정 실사고(심의가 발표자료 생성기로 간 것 · 물성 질의에 지어낸 값), 고치기 전 순위권 밖이던 업무 낱말(a8ecccf), 어휘 일치 0건이던 질의(에이전트 서버 f28786e), 그리고 문서가 정답이라고 적은 짝(첫 실검증 질의 · 심의 좌석의 분야별 도구 · StepForge 질문→도구 안내)이다.
- `source: auto` — 앱마다 도구를 시드 고정 무작위로 고르고(앱 도구 수의 제곱근 × 1.5, 최소 3 — 진단용 echo 도구 둘은 뺐다), **순위 방법을 모르는 별도 에이전트**가 그 도구의 설명만 보고 '하고 싶은 일' 을 한국어 업무어로 썼다. 도구 이름·식별자를 쓰지 않고 설명의 세 어절 이상을 그대로 옮기지 않게 했고, 절반쯤은 기능이 아니라 처한 상황을 말하게 했다. 정답은 초안을 쓴 도구이고, 같은 일을 하는 다른 도구가 분명한 13쌍은 **결과를 보기 전에** 정답에 더했다(`note` 에 적었다).
- 모든 쌍이 `reviewed: false` 다 — 사람이 질의와 정답을 고치면 `true` 로 바꾼다. 특히 정답이 하나뿐인 쌍은 지금 카탈로그에서 다른 도구도 맞는 답일 수 있다(위 '읽는 법' 3).
- 정답 도구가 지금 카탈로그에 없으면 그 쌍은 재지 않고 러너가 따로 센다(DynaForge·ReportArchive 가 내려간 dev 에서 doc 8쌍).
- 실사용 질의는 없다 — 게이트웨이 감사 원장은 `search_tools` 호출과 인자를 남기지 않는다(로컬 도구라 감사 밖이다). 실사용 질의를 모으면 `*.local.jsonl`(추적하지 않는다)로 두고 `--pairs` 로 잰다.

## BGE-M3 로 다시 잼(2026-10-18 — 결정 21 '끈 채 재측정')

dev AIDataHub 임베더가 BGE-M3(1024차원)로 바뀐 뒤(포털 `docs/embedder-bge-m3`), **같은 카탈로그(10-16 스냅샷) · 같은 142쌍**으로 다시 쟀다
(`run.py eval --embed-url …/api/embed` — 게이트웨이 코드는 그대로, 차원이 바뀌면 색인을 다시 채운다). 부분문자열 줄은 임베더와 무관해 그대로다.

| 방법 | 출처 | n | hit@1 | hit@5 | MRR@20 |
|---|---|---|---|---|---|
| 부분문자열(지금) | doc | 34 | 0.471 | **0.882** | **0.651** |
| RRF(옵션) e5 → **m3** | doc | 34 | 0.382 → **0.500** | 0.706 → **0.765** | 0.539 → **0.621** |
| 임베딩만 e5 → **m3** | doc | 34 | 0.147 → 0.382 | 0.412 → 0.559 | 0.255 → 0.459 |
| 부분문자열(지금) | auto | 108 | 0.194 | 0.389 | 0.298 |
| RRF(옵션) e5 → **m3** | auto | 108 | 0.296 → **0.417** | 0.713 → **0.769** | 0.466 → **0.572** |
| 임베딩만 e5 → **m3** | auto | 108 | 0.380 → 0.602 | 0.667 → 0.824 | 0.495 → 0.707 |

doc 을 갈라 보면 둘이 반대로 간다.

| doc 묶음 | n | 부분문자열 hit@5 · MRR | RRF(m3) hit@5 · MRR | RRF 쌍마다 |
|---|---|---|---|---|
| 심의 업무 낱말(doc-01~14 — `_SYN` · APP_META 로 손댄 낱말) | 14 | **1.000 · 0.738** | 0.643 · 0.443 | — |
| 그 밖(실사고 · 어휘 0건 · 문서 적은 짝) | 20 | 0.800 · 0.591 | **0.850 · 0.745** | 나아짐 7 · 나빠짐 1(e5 는 3 · 5) |

- **판정 — 그대로 끈다.** 손댄 낱말에서는 부분문자열이 이기고, 손대지 않은 질의에서는 이제 RRF 가 이긴다. 실사용 질의가 어느 쪽에 가까운지는
  모은 질의로만 안다(결정 21 의 질의 수집) — 그 뒤에 '부분문자열 순위 가중'(위 e5 표의 가중 2 꼴)을 m3 로 다시 잰다.
- RRF 한 번의 시간 — 중앙 37ms · p95 44ms(임베딩 질의 포함, dev CPU). 한도(`GATEWAY_TOOL_SEARCH_EMBED_TIMEOUT` 2초) 안이다.
- 150쌍은 아직 사람이 보지 않았다(`reviewed:false` 전부) — 위 숫자는 검토 전 평가셋의 것이다.

## 러너 — `run.py`

```bash
PY=../HWAXAgentServer/.venv/bin/python        # 게이트웨이와 같은 파이썬
# 1) 카탈로그 스냅샷 — 떠 있는 게이트웨이의 tools/list + /tools-map. 토큰은 설정 파일에서 읽는다(인자로 받지 않는다)
$PY tool_search_eval/run.py snapshot --gateway http://127.0.0.1:9110 --config gateway_config.json
# 2) 견주기 — 임베더를 주면 RRF 와 임베딩 순위(진단)도 잰다. --detail 은 쌍마다 방법별 순위
$PY tool_search_eval/run.py eval --embed-url http://127.0.0.1:8001/api/embed --detail
```

- 러너는 `gateway` 를 import 해(임시 설정, 백엔드·포털 없이) 스냅샷을 카탈로그로 앉히고 `_search_tools(limit=20)` 를 옵션을 끄고 한 번, 켜고 한 번 부른다 — 재는 것이 배포되는 코드 그 자체다. 앱 라벨·설명(app_hit)도 라이브의 `/tools-map` 값 그대로다.
- 지표는 1위 적중(hit@1) · 5위 적중(hit@5) · MRR@20(정답 가운데 가장 앞선 것의 순위의 역수, 20위 밖은 0)이고 `doc`·`auto`·전체로 따로 낸다. RRF 대 부분문자열을 쌍마다 견준 수(나아짐·나빠짐·같음)와 `search_tools` 한 번의 시간도 낸다.
- 잴 때의 질의 임베딩 한도는 30초다(`--embed-timeout`) — 방법을 재는 것이라 시간 초과로 섞이지 않게 넉넉히 두고, 시간은 따로 찍는다. RRF 가 부분문자열로 떨어진 질의가 있으면 러너가 센다.
- 스냅샷(`catalog.local.json`)은 추적하지 않는다 — 내부 도구 설명 전문이고 카탈로그가 바뀌면 낡는다.

## 켜기

손잡이는 리포 README 의 'search_tools 의미 순위' 절 — `GATEWAY_TOOL_SEARCH_EMBED_URL`(비면 꺼짐) · `GATEWAY_TOOL_SEARCH_EMBED_TIMEOUT`(기본 2초). 게이트웨이는 `.env` 를 읽지 않으므로 띄우는 프로세스의 env 에 있어야 한다.
